# LLM 실측 기록 (2026-11-17)

LLM 보조 추출(설계서 7.3절 B)과 LLM 초안(7.5~7.6절)을 실제 Claude API로 처음 돌려 품질·시간·비용을 쟀다.

- **입력:** 공개 RFP 실물 1건(PDF 404쪽, 본문 약 37만 자, 「차세대시스템(1단계) 구축 사업」). 평가표 7부문·28항목·100점, 표 요구사항 242건
- **모델:** Models API가 고른 최신 Opus 계열(저장소에는 모델 ID를 적지 않는다. 호출별 모델은 프로젝트의 `audit/llm_calls.jsonl`에 남는다)
- **비용:** 감사 기록의 토큰 수와 측정 당시 공개 단가(백만 토큰당 입력 $4, 출력 $20, 캐시 읽기 $0.2, 캐시 쓰기 $5)로 계산한 추정값이다. 실제 청구액은 Console에서 확인한다
- **데이터 범위:** 공개 RFP만 보냈다(`--llm-share-kb` 없음). KB 값·설명은 보내지 않았다

## 1. LLM 보조 추출(`rfpgen analyze --llm`)

| 과제 | 설정 | 호출 | 시간 | 토큰(입력 / 캐시 쓰기·읽기 / 출력) | 결과 |
|---|---|---|---|---|---|
| 작성지침 | medium, 16K | 1 | 17초 | 1.3K / 51K 쓰기 / 1.7K | 결정적 추출이 채운 값과 같아 새로 채운 값 없음. 추가 작성 요건 11건(LLM-GUIDE-MANUAL) |
| 무효·감점·참가자격 | high, 32K, 2회 | 2 | 87초, 91초 | 1.1K / 52K 쓰기 → 2회째 52K 읽기 / 10.9K, 12.0K | 근거 검증을 통과한 조건 12건, 참가자격 2줄, 권고 5건. 두 번 중 한 번만 나온 4건은 LLM-UNSTABLE |
| 문장형 요구사항 | high, 32K | 1 | 227초 | 0.7K / 53K 쓰기 / **32K(잘림)** | 실패 — 사고 토큰을 포함한 출력이 상한에서 잘림 |
| 문장형 요구사항(다시) | medium, 64K | 1 | 296초 | 0.7K / 53K 쓰기 / 41.9K | ID 없는 요구사항 후보 157건 |

- 분석 전체(첫 실행): 호출 4회, 7분 28초, 약 $1.94. 문장형 요구사항 재실행 약 $1.11
- 같은 발췌를 두 번 보내는 무효·감점 과제는 두 번째 호출이 캐시를 읽었다(프롬프트 캐싱 동작 확인)

### 품질

- **숫자를 지어내지 않았다.** 이 RFP는 쪽수 상한·발표 시간·지분율 같은 숫자가 도형 글자라 텍스트에서 빠져 있다. 작성지침 과제는 "원문에서 숫자가 비어 있어 출력하지 않음"으로 남겼고, 무효·감점 과제도 "(원문 수치 공란)"으로 적었다. 쪽수 상한은 계속 GUIDE-PAGE-UNREADABLE로 사람에게 넘어간다.
- **결정적 추출이 놓친 요건을 찾았다:** 제본본 15부 추가 제출, 우편 제출 불가·제출처, 쪽 번호 하단 중앙, 홍보 동영상 금지, 발표용 노트북은 발주기관 것 사용, 계량평가 제안서 별도 제출 등 11건.
- **무효·감점 분류가 넓었다.** 부정당업자 제재·계약 해지·실적 불인정·비용 부담이 '감점'으로 들어갔다. 스키마에 '불이익'이 없었기 때문이다 → '불이익' 분류를 더했다.
- **문장형 요구사항 157건**(기능 33, 보안 28, 프로젝트 지원 20, 제약 16, 인터페이스 15, 관리 13, 데이터 11, 테스트 9, 품질 8, 성능 4). 낱말 유사도로는 표 요구사항과 겹치는 것이 없었지만(최대 0.17), 상위 후보를 직접 보면 '상용 DBMS 요건 ↔ ECR-03-010', '교육 ↔ PSR-009'처럼 뜻이 겹치는 것이 있다. 모두 `status=proposed`·G1 검토 대상이며, 병합 후보 표시가 필요하다.

## 2. LLM 초안(`rfpgen draft --llm --section …`)

배점이 고르게 5점이어서 성격이 다른 세 절을 골랐다: Ⅳ.3 시스템 장비 구성 요구사항(요구사항 23건), Ⅲ.3 추진체계(도식 포함), Ⅵ.2 사업수행책임자(PM) 역량(KB 인력).

| 호출 | 설정 | 시간 | 출력 토큰 | 결과 |
|---|---|---|---|---|
| 스토리보드 | high, 32K | 183초 | 20.5K | win theme 3개, 절별 거버닝 메시지·핵심 내용, 자료 요청 90건 |
| Ⅲ.3 추진체계 | high, **8K** | 73초 | 8.0K(잘림) | 실패 → 골격으로 대체 |
| Ⅳ.3 장비 구성 | high, **8.6K** | 74초 | 8.6K(잘림) | 실패 → 골격으로 대체 |
| Ⅵ.2 PM 역량 | high, 8K | 64초 | 7.2K | 성공 |
| Ⅲ.3 추진체계(다시) | high, 32K | 51초 | 5.4K | 성공 |
| Ⅳ.3 장비 구성(다시) | high, 32K | 96초 | 11.4K | 성공, 23건 대응 방안 |

- 초안 비용: 첫 실행 약 $1.03, 다시 쓴 두 절 약 $0.38
- 절 상한을 요구사항 수로 줄이던 계산(최소 8K)이 원인이었다. 사고 토큰이 상한에 들어가므로 프로필 값(32K)으로 바꾸고, 잘리면 상한을 두 배로 한 번 다시 보내게 했다.

### 품질

- **형식과 문체:** 개조식(□ ○), 명사형 종결, RFP 용어(PMR-004, COR-002, QUR-007·008 등 요구사항 ID 인용)를 지켰다. 표를 적절히 썼다(요건 충족 현황, 이해관계자별 소통 방식 등).
- **블라인드:** 회사명·제품명·사람 이름 없이 "당사"로 썼다. 블라인드 점검(BLD-001) 지적 없음.
- **근거 없는 수치:** KB 값을 보내지 않았으므로 PM 경력·실적은 `[확인 필요: …]`로 남겼다(절당 9~22곳). 지어낸 회사 수치는 없었다. 근거 없는 수치 점검(FACT-002)이 '242건', '3건', '노드 1대'를 잡았고, '1:1 대응'을 수량으로 잘못 잡던 오탐은 고쳤다.
- **요구사항 대응:** Ⅳ.3의 23건 모두 RFP 세부 내용(이중화, 100% 확장 여유, 라이선스 범위, 통합배선 비용 부담 등)에 맞춘 대응 방안을 냈다. 수용 여부는 모두 '수용'이었고 "비용은 당사가 부담" 같은 약속이 들어 있어, 절 승인(G4) 때 사업 조건을 사람이 확인해야 한다.
- **과장 표현:** '최고' 1건(LANG-003)을 잡았다.
- **자료 요청 90건:** 절마다 LLM이 필요 근거를 많이 적어 자료 요청서가 길다. 중복 병합·상한이 필요하다.

## 4. 추정과 다음 과제

- **전체 37절 LLM 초안 추정:** 절당 50~100초, 0.2~0.4달러 → 직렬로 약 45분, 약 8~15달러(요구사항이 많은 절일수록 크다). 스토리보드 1회 약 0.5달러 별도.
- **다음 과제**
  1. 문장형 요구사항에 표 요구사항 ID·이름 목록을 함께 보내 같은 요구는 병합 후보(`same_as`)로 표시
  2. 스토리보드 자료 요청을 비슷한 항목끼리 묶고 상한을 둠
  3. 서로 독립인 호출(분석 과제 3종, 절 초안)을 동시에 보내 시간 단축
  4. `--llm-share-kb` 모드 실측: KB 토큰(`{{fact:…}}`)을 써서 `[확인 필요]`가 얼마나 줄어드는지
  5. 공개 RFP 라벨 30건 벤치마크(M1 완료 기준)
